# integration-reviewer reads only, and takes limits from the repo's docs rather than Project config

integration-reviewer's tools are Read, Grep, Glob and WebFetch: no shell and no file-editing tools, so it is read-only by its tool list and needs nothing from the guard hook. The caller, which has git, passes the diff (or the base ref and the changed files). We rejected giving it Bash for `git diff` behind the guard (as live-verifier and data-digest have, ADR 0009): it would add a third agent to a hook that starts on every tool call, for a reviewer that needs only to read files; and the guard allows programs by bare name only, so where bare `git` doesn't work (the eval sandbox on macOS) the reviewer couldn't run git at all. Each system's limits (rate limits, batch sizes, retry rules) come from the docs the caller names, then the repo's own docs, then the wrapper's own constants, then the vendor's current public docs, cited. A limit it can't find in any of these is a question, never a finding. We rejected a tenth Project config section for API limits: section names are a contract for every skill (ADR 0006), limits are per endpoint and plan and change often, and the repos that care already document them next to their wrappers. So for limits, "reached through Project config" (ADR 0003) becomes "reached through the repo's own docs": the Harness still ships no platform's limits.
