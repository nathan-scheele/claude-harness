# An advance go-ahead counts for one named Live write

The Live-write gate (S1) is met by a go-ahead the operator gives before the agent reaches the write, as long as it is given in the current conversation and names that specific write, accepts its effect, and states any condition: "once CI is green you have my go-ahead to squash-merge the PR for issue 11 into main; I know that deploys". The agent still posts its summary of exactly what will change, and goes ahead only if the facts match the condition; if they don't (CI red, a different PR, something else would deploy), it stops and asks as usual. A request to start the work ("ship it", "merge it", "do it, dry run first") is not a go-ahead for the Live writes inside it, because it comes before the operator has seen what will change; nor is a go-ahead given for an earlier write or in another session. We accepted this because the operator often approves a known next step up front (gated-write's canary and full run, ship-and-land's merge), and because single-turn evals can only exercise the steps after a gate this way. We rejected a strict always-stop gate (it makes the operator repeat a decision already made explicitly) and leaving the practice unrecorded (S1 and the skills would disagree).
